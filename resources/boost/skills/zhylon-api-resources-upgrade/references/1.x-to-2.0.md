# Upgrade zhylon/api-resources from 1.x to 2.0

Agent instructions. Work through the steps in order. Steps marked with **ASK** need a decision of the user.
Background for every step: [UPGRADING.md](https://github.com/Zhylon/api-resources/blob/main/UPGRADING.md#from-1x-to-20).

The output of existing resources does not change in 2.0. The breaking changes only affect code that overrides or extends the package. The goal of this upgrade: same API output as before, no failing tests.

## Step 1: Check the requirements

2.0 requires PHP 8.2+ and Laravel 12 or 13 (unchanged from 1.x). If the app runs an older Laravel version: **stop** and tell the user. Do not upgrade Laravel as part of this task.

## Step 2: Find all usages

Search the app (not `vendor/`) and keep the results for the next steps:

```sh
grep -rln "Zhylon\\\\ApiResources" app/ routes/ bootstrap/ tests/ --include="*.php" 2>/dev/null
grep -rnE "use BuildsApiResource;|extends ApiResourceCollection|toApiResource\(" app/ --include="*.php" 2>/dev/null
```

For every resource class using `BuildsApiResource` and every class extending `ApiResourceCollection`, note whether it defines:

- `with(`
- `toArray(` (only for `ApiResourceCollection` subclasses)
- any of `withMeta(`, `withLinks(`, `apiTopLevel(`, `apiDocument(`, `apiIncludedResources(`, `relationship(`, `newRelationship(`, `loadedRelation(`, `resolveRelationships(`, `sparseFieldsFor(`
- a property `$apiIncluded`, `$apiDocument`, `$apiTopLevelMeta` or `$apiTopLevelLinks`

Also note `toApiResource(` calls whose `attributes` contain `fn (` or `function (`, and places that spread the result of `toApiResource()` and add `relationships`, `included` or `meta` by hand.

## Step 3: Update the package

```sh
composer require zhylon/api-resources:^2.0 -W
```

If composer fails because of other packages, report the conflict to the user. Do not remove or downgrade other packages without asking.

## Step 4: Fix `with()` overrides

`BuildsApiResource` now defines `with()`. A resource's own `with()` replaces it, so `included` and top-level `meta`/`links` would be missing. Keep the existing output and merge the new members:

```php
public function with($request): array
{
    return array_merge_recursive([/* existing return value */], $this->apiTopLevel($request));
}
```

Do the same for `with()` in subclasses of `ApiResourceCollection`.

## Step 5: Fix `ApiResourceCollection` subclasses

`toArray()` of `ApiResourceCollection` now returns `['data' => array]` with rendered items instead of a collection of resources.

- Subclasses that override `toArray()` and call `parent::toArray()`: check that they don't call collection methods on `data`. Use `$this->collection` (still a collection of resources) if they need the resources.
- Subclasses that override `toArray()` without calling the parent: nothing breaks, but `included` won't work for them. Leave them as they are and mention it in the report.
- Tests that assert `toArray()['data']` is a `Collection` or contains resource objects: assert the rendered arrays instead.

## Step 6: Fix name collisions

For each method or property found in step 2 that the trait now defines:

- If it does the same as the trait's version (e.g. a hand-written `withMeta()` that adds top-level meta), **ASK** whether to remove it in favor of the package.
- Otherwise **ASK** whether to rename it, and update all callers. The resource's own method wins over the trait, so leaving it is safe for the output, but the package features with that name won't work in that resource.

## Step 7: Check closures in attributes

Closure values in `attributes` were serialized as `{}` in 1.x and are evaluated in 2.0. This changes the output. For each one found in step 2, **ASK** the user: usually the closure was a bug (the intended value is the result of the closure), so evaluating it is what they want.

## Step 8: Tests

- Run the test suite and static analysis.
- Snapshot or exact JSON tests of collections must still pass unchanged. If they fail, find the cause (usually step 4 or 5) instead of updating the expected JSON.
- Fix failures caused by the upgrade, report others.

## Step 9: Optional improvements

Only suggest these to the user, do not apply them without asking. Each one changes the API output:

- Hand-written `relationships` (spread of `toApiResource()` plus a `relationships` key) → `relationships:` parameter with `$this->relationship(...)`. The output stays nearly the same, compare it.
- `additional(['included' => ...])` or similar → `->resource(SiteResource::class)` on the relationship.
- Custom JSON error rendering in `bootstrap/app.php` or the exception handler → `$exceptions->render(new \Zhylon\ApiResources\Http\Errors\ApiExceptionRenderer)`. **Changes the error format for all API clients.**
- Manual handling of `?fields[type]=` → `SparseFieldsets::enable()`.
- `meta` with permissions etc. added by hand → `meta:` parameter of `toApiResource()`.

## Step 10: Report

Use the report format of [SKILL.md](../SKILL.md#3-report). Always include:

- every `with()` override you changed,
- every name collision and what the user decided,
- `ApiResourceCollection` subclasses that won't render `included`,
- which optional improvements the user may want to apply later.
